# Naming 与 Goal 历史选择成本

2026-09-06，`ps-yon.20` 在既有选择器中移除了两处扫描已丢弃历史的工作。Naming 从后向前查找六条
user/assistant 消息，再恢复时间顺序。Goal 恢复找到最新规范条目即停止；同一次遍历记住最新旧版条目，
仅在不存在规范条目时使用它。两处都没有新增缓存。规范校验、无效状态处理、队列规范化及首次 Naming 的
短对话规则不变。

基线为 `67944dfeda231fd2feb026306ee167068e86087c`。
[数值记录](../../../../../docs/reports/history-selection-cost-2026-09-06.json)保留全部 165 组配对试验、输入／输出
哈希、源码哈希及单独的完整 Suite Goal 样本。这是局部成本削减，不代表
[16 个 Capability 审计](suite-resource-inventory-2026-09-05.md)完成。

## 选择器测量

精确 Pi 0.85.0 可执行文件的 SHA-256 为
`0cfd1bf3e9468f1052d172502fa388e8e8e53dcdeb9fa97f1ef828fdd7757072`，在内嵌 Bun 1.3.14 下加载临时诊断
Extension。对照模块保留基线函数体，只修改导入路径和末尾空行；计时前已完成导入。测量调用真实生产选择器，
输入为合成数组，不包含 Pi 的 `getBranch()` 构建成本或完整 Suite。

分支含 100、1,000 或 10,000 条交替 user/assistant 消息。Goal 场景把最后一条替换为规范或旧版状态，包含
一个暂停的主 Goal 和八个排队 Goal；无状态场景不含 Goal 条目。数字索引访问用 Proxy 单独计数。计时使用
普通数组，每个版本预热 20 次，然后进行 11 组交替先后顺序的配对试验，每次调用 100 次；哈希不在计时区间。
进程 CPU 包含运行时后台线程，因此可超过墙钟时间。

| 10,000 条目场景 | 每次调用的索引读取，前 → 后 | 每 100 次调用的耗时中位数，ms | 每 100 次调用的进程 CPU 中位数，µs |
| --- | ---: | ---: | ---: |
| Naming，首次 | 10,000 → 6 | 17.215 → 0.018 | 22,865 → 18 |
| Naming，周期／强制 | 10,000 → 6 | 16.705 → 0.015 | 25,042 → 15 |
| Goal，最新规范状态 | 10,000 → 1 | 5.441 → 3.097 | 5,451 → 3,090 |

每次计时结果的输出哈希均与对照相同，输入哈希始终不变。Naming 穷举比较覆盖长度零至八的 user、assistant
和 custom 序列，在首次／周期模式下共 19,682 个场景，结果全部相同。较小场景也保留在数值记录中，其中
1,000 条目的旧版 Goal 场景 CPU 从 3,611 增至 4,150 µs；不声称 CPU 一律改善。较长的纯 custom 尾部仍须
扫描，旧版／无状态 Goal 选择仍为 O(分支条目数)。Goal 计时仍包含必要的队列校验和规范化。

中间版 `findLast` 实现通过原生诊断，但未通过 Goal 模块的 ES2022 类型检查。最终改为单次反向循环，没有
升级 target 或添加兼容层。早期诊断还遇到 Jiti 初始化失败，以及 RPC stdin 未关闭而被超时终止；这些失败
尝试保留在私有证据中。最终循环版测量关闭 stdin，并以零退出。

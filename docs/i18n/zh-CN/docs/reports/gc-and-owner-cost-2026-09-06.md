# GC 观测与保留的 owner 成本

2026-09-06，三个基于 `3789e99e` 的诊断运行把自然垃圾回收记录与现有外部 Spinner／输入观察器放在一起。
本轮未复现之前的 270／489 ms 停顿，日志中最大的 GC 暂停为 20.157 ms。这既不能确定历史停顿的原因，
也不能证明它们不会再出现。本轮没有修改生产代码。

[数值记录](../../../../../docs/reports/gc-and-owner-cost-2026-09-06.json)保留源码与证据哈希、GC 计数、
资源范围统计，以及独立的 Notification、Codex 和 Web owner 测量。这些证据补充
[资源清单](suite-resource-inventory-2026-09-05.md)，完整审计仍未结束。

## 精确 Host 中的自然 GC

全部运行使用同一个精确 Pi 0.85.0 可执行文件，SHA-256 为
`0cfd1bf3e9468f1052d172502fa388e8e8e53dcdeb9fa97f1ef828fdd7757072`，内嵌 Bun 1.3.14，终端尺寸为 120×40，
各发起两次 Tool 请求。运行串行进行，使用独立的新配置与临时缓存；不清空 OS 页缓存，也不控制机器上的其他活动。
本地没有测试、调查子代理、分析器或其他基准与采样并行。

临时观察器补丁向 Pi 传入 `JSC_logGC=1`，把 stderr 重定向到单独文件，并在每次外部帧捕获后读取新增字节。
GC 文本因此不会进入 TUI。日志读取的到达区间与观察器共用时钟，但不是精确的 GC 起始时间。
最慢一次日志读取为 0.258 ms。未强制回收、生成堆快照或调整 GC 策略。日志开销未被界定，故这些运行是诊断，
不是验收样本。

Bun 的 [1.3.14 构建配置](https://github.com/oven-sh/bun/blob/bun-v1.3.14/scripts/build/deps/webkit.ts)
固定 WebKit `5488984d20e0dbfe4be2c3ba8fb18eb81a5e0e8b`。其
[Heap 实现](https://github.com/oven-sh/WebKit/blob/5488984d20e0dbfe4be2c3ba8fb18eb81a5e0e8b/Source/JavaScriptCore/heap/Heap.cpp)
以 `p=` 记录实际暂停，以 `cycle` 记录整个回收区间，两者含义不同。
[调度器](https://github.com/oven-sh/WebKit/blob/5488984d20e0dbfe4be2c3ba8fb18eb81a5e0e8b/Source/JavaScriptCore/heap/StochasticSpaceTimeMutatorScheduler.cpp)
的 `tp=` 是目标暂停，解析器不把它计入实际暂停。`ca=` 读取回收开始时的堆分配记账值并除以 1,024，
不是存活堆大小。

下表只统计最后一次外部捕获前读到的日志前缀，不计关闭阶段的尾部字节。
不同 VM 的暂停可能重叠，相加不能得到 CPU 时间或主线程独占的阻塞时间。原生运行的父进程 stderr 出现一个堆，
两个 Suite 运行各出现两个堆；这些标识不能把成本分给具体 Capability，也不包含 Agents 单独捕获的子进程 stderr。

Bash 对照表明，没有 Suite 时也会频繁进行小型回收。Suite 的额外工作仍有成本：原生资源范围 CPU 为 3.013 秒，

这组单次、带诊断开关的样本不能把全部差值归为浪费，也不能证明稳定的 CPU／内存差异。

不只包含导入。按日志到达时间分组，Agent 运行区间的对应总和依次为 107,271、153,008、646,189 KiB。
并发回收期间的分配、尚未回收的尾部、原生分配和子进程堆不在这些总和内，因此它们不是完整分配量或保留内存量。
下文的后续测量区分了主要启动边界。

最后一次运行进一步细分 Context 激活。启动准备在 5.117 ms 内决定延后首次配置，直接输入后的准备为

GC 日志到达边界也划分了首个 Spinner 前的大区间。完全落在 Suite runtime 导入期内的读取，其 `ca=` 总和为

完整分配量与 Worker 独占 CPU 仍未测量。

[Suite loader](../../../../../packages/pi-stuff/src/suite-loader.ts)以条目路径、文件系统元数据和符号链接目标
计算指纹，不读取源码正文。探针移除后的只读枚举发现 648 个条目、含根目录在内的 61 个目录，无符号链接。

日志与标记开销仍未被界定，故这些不是锁定门槛的验收样本。三个资源范围均确认已卸载。
本轮没有运行 Agent 子进程、冷 Ledger 恢复或真实服务；历史后段停顿仍未解释。

## 保留的 owner 行为

另一个临时 Extension 把生产 owner 函数加载到同一精确 Pi VM 中，并断言 Bun 1.3.14。
它在用户／网络／PID 命名空间中使用合成 Host、时钟和服务回调。这是 owner 边界证据，不是完整 Suite 或真实服务验收。
第一次尝试设为 `PI_OFFLINE=1`，正确触发了 Codex 离线保护；成功运行在断网命名空间中设为 `PI_OFFLINE=0`，
结束时没有 Extension 错误。

Notification 实际 runtime 分别处理 1、100、1,000 次符合条件的结算。每次结算只安排并触发一个宽限计时器，
发出一次提醒。每组另建一个待处理周期并调用 dispose：取消一个计时器，最终没有待处理计时器。
直接终端输入取消投递，自动重启保留 35 ms 工作时长，纯自动或重复的空闲事件不安排计时器。
保留宽限计时器；这些场景未发现重复调度或周期轮询。受控时钟不测量 OS 唤醒或终端输出。

Web 的实际工厂注册 fetch／retrieval Tool 与 Session 生命周期处理器。每个合成 fetch 结果含 512 个内容字符。
驱动调用这些已注册 Tool，没有重写另一套发布实现：

| Fetch 发布数 | 夹具统计的 canonical 载荷字节 | 过期恢复访问的条目数 | 过期恢复后／关闭后保留数 |
| ---: | ---: | ---: | ---: |
| 100 | 66,890 | 100 | 0 / 0 |
| 1,000 | 670,890 | 1,000 | 0 / 0 |
| 10,000 | 6,728,890 | 10,000 | 0 / 0 |

发布时，内存 Map 与合成 `appendEntry` 收到的是同一个 `StoredSearchData` 对象。这排除了该 owner 边界上的
又一次载荷克隆，不代表其他路径没有复制，也不包含 Pi 持久化成本。已注册的 retrieval Tool 正常返回，切换到单条分支
会替换旧索引，关闭释放所有索引结果。超过一小时后，实时查询仍能返回旧结果；TTL 只在恢复时生效，不限制实时查询。
提前清除实时结果会改变该行为。保留发布、查询与分支校验；当前证据不支持改变 TTL，也不能确定整个 Session 的堆上限。
搜索、DNS、提取、远程 HTTP 与原生 Session 写入不在本夹具范围内。

Codex 直接 usage 函数调用一次提供的 fetch 回调，读取一次 71 字节响应体，生成预期的周用量。
它不覆盖 Extension 的并发刷新合并逻辑。上文完整 Suite GC 工作负载分别验证一次自动 HTTP 刷新，但没有解决并发请求成本。

Notification／直接 usage 组合夹具耗时 6.979 ms，进程 CPU 为 12,864 µs；Web 夹具为 90.754 ms 和 248,129 µs。
这些单次区间包含夹具构造、断言和载荷字节统计，导入已在计时前完成。CPU 包括进程的全部线程。
数值记录保留 `getrusage` 计数；上下文切换不是精确唤醒次数，`maxRSS` 是进程整个生命周期的高水位。
这些计时不支持单个 owner 内存节省或优化前后收益的结论。

整个进程的分配量、精确唤醒、模块求值细节、其余 owner／恢复工作负载和历史后段停顿，仍由 `ps-yon.3` 与 `ps-yon.6` 跟进。
